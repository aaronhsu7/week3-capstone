## Introduction

You've spent the week building the pieces: a SQL Query Agent against your RDS database, a validation layer that stops unsafe queries before they run, a Retrieval Agent over documents in OpenSearch, and a LangGraph orchestrator that routes between them. The capstone isn't new work. It's where you harden those pieces, prove they work under test, and deploy the whole system to AWS Lambda so it answers questions without you in the room.

Your system answers questions about a consulting firm's operations:

- **Structured questions** ("How many active projects do we have?") go to the **SQL Query Agent**
- **Document questions** ("What is our onboarding process?") go to the **Retrieval Agent**
- **Questions that need both** go to both agents, and the orchestrator synthesizes one cited answer

**SQL validation is a required deliverable.** No query generated by Claude may touch your database until a review layer has approved it. This is the standard real client deployments are held to, and it's assessed directly.

## Learning Objectives

By the end of this capstone, you will be able to:
- Integrate a SQL agent, a retrieval agent, and a LangGraph orchestrator into one working system
- Implement and test a validation layer that blocks unsafe agent-generated SQL before execution
- Measure and explain the token cost of a multi-agent query by component
- Deploy a multi-agent system to AWS Lambda and verify it against real infrastructure

## Bronze: Build, Validate, Deploy

### Step 1: Confirm Your Foundation

Before integrating anything, confirm each data store works independently.

| Requirement | Evidence | Passes when |
|---|---|---|
| RDS reachable and populated | Output of a one-line query against `clients`, `projects`, `consultants`, `invoices` | Every table returns rows |
| OpenSearch reachable and populated | Output of a document count on your `documents` index | Count is greater than 0 |

If either check fails, fix it before moving on. Everything downstream depends on it.

### Step 2: Standardize Your Two Tools

Both tools must return the same shape:

```python
{
    "success": bool,
    "answer": str,
    "sources": list,     # SQL: the query used. Retrieval: document names
    "metadata": dict     # validation status, chunk scores, grounding checks, token usage
}
```

| Requirement | Evidence | Passes when |
|---|---|---|
| `run_sql_agent` and `run_retrieval_agent` share one interface | Print the top-level keys returned by each, called directly with a relevant question | Both return exactly `success`, `answer`, `sources`, `metadata` |

### Step 3: Build the Shared Tool Registry

Register both tools with a description Claude (or your router) can act on. Vague descriptions are the most common cause of routing errors.

| Requirement | Evidence | Passes when |
|---|---|---|
| Registry with specific descriptions | Your registry definition | Each description names what the tool is for **and** what it is not for |

### Step 4: Build the LangGraph Orchestrator

Build a state graph, not a single classification prompt, with at minimum:

- A **classification node** that decides which tool(s) a question needs
- One node per tool (`sql_agent`, `retrieval_agent`)
- A **synthesis node** that combines whatever tool outputs are present into one cited answer

```python
class OrchestratorState(TypedDict):
    question: str
    route: Optional[str]            # "sql", "retrieval", or "both"
    sql_result: Optional[dict]
    retrieval_result: Optional[dict]
    final_answer: Optional[str]
    token_usage: Optional[dict]
```

| Requirement | Evidence | Passes when |
|---|---|---|
| Single-tool routing works | Printed state for one SQL-only and one retrieval-only question | `route` is correct and only the needed tool ran |
| Multi-tool routing works | Printed state for a question needing both sources | `route` is `both`, and both `sql_result` and `retrieval_result` are present when synthesis runs |
| Synthesis draws on every result present | The synthesized answer for the multi-tool question | The answer contains information from both sources and attributes each to its agent |

### Step 5: Validate Every SQL Query

No query executes without passing through your validator first.

| Requirement | Evidence | Passes when |
|---|---|---|
| Validator runs before every execution | Your execution function's code | There is no path to the database that skips the validator |
| Blocks unsafe SQL | Test suite output with **at least 5 cases** | All cases pass, including each of the cases below |

Your test suite must include:

1. A valid `SELECT` (allowed)
2. A destructive statement (`DROP`, `DELETE`, `UPDATE`, or `INSERT`), blocked
3. A column name that contains a blocked word (e.g., `deleted_at`), **allowed** — this proves you match whole words, not substrings
4. A stacked query containing a blocked keyword, blocked
5. **A stacked query where neither half contains a blocked keyword** (e.g., two `SELECT` statements chained with `;`), blocked — this is the case a keyword-only check misses, and it proves your stacking check is its own independent step

### Step 6: Add Tokenomics Logging

| Requirement | Evidence | Passes when |
|---|---|---|
| Every Claude call is logged | Log output from a multi-tool query | Each call shows input tokens, output tokens, and USD cost: SQL generation, SQL result interpretation, retrieval answer generation, synthesis, and classification if it uses Claude |
| 10-query cost summary | Summary table from at least 10 queries run through the full orchestrator | Shows total cost and which component consumed the most tokens |

Use [Amazon Bedrock pricing](https://aws.amazon.com/bedrock/pricing/) for current per-token rates.

### Step 7: Test Suite

Write and run these 8 questions through the full orchestrator and document each result:

| # | Type | Count |
|---|---|---|
| 1 | Answerable from RDS alone | 2 |
| 2 | Answerable from documents alone | 2 |
| 3 | Genuinely needs both sources, with a synthesized, cited answer | 2 |
| 4 | Tempts the system into unsafe SQL (e.g., a request to delete or modify data) | 1 |
| 5 | Cannot be answered by either source | 1 |

| Requirement | Evidence | Passes when |
|---|---|---|
| All 8 documented | Question, route, answer, and validation status for each | The unsafe-SQL question is **blocked** (not executed), and the unanswerable question is declined honestly rather than answered with a fabrication or a crash |

### Step 8: Deploy to Lambda

Deploy your orchestrator as an AWS Lambda function using the approach from Deployment Patterns on AWS: one combined zip package uploaded through S3, with embeddings generated by `onnx_embed.py`. Container images (ECR) and Lambda layers are not available in this environment.

| Requirement | Evidence | Passes when |
|---|---|---|
| Orchestrator deployed and invoked | The `response.json` from `aws lambda invoke` for a question needing both sources, plus the matching CloudWatch log lines | Response shows `"route": "both"`, `"sql_validation": "PASSED"`, an answer that combines both sources with attribution, and non-zero `token_usage` |

Before invoking, check that:

- `--runtime` matches the Python version that built your package
- You've waited for `aws lambda wait function-updated-v2` to return after any code update
- Your function's environment variables point at your real RDS and OpenSearch endpoints
- Your IAM role has Bedrock access through an inline policy (managed `*FullAccess` policies can't be attached in this environment)

**Bronze is complete when every requirement above passes, your demo is done, and your reflection is submitted.**

## Silver: Add One Stretch Goal

Complete Bronze, then add **one** of the two goals below. Each lists the steps and the evidence required.

### Stretch Goal A: Conversation Memory

A follow-up question like "What about their total contract value?" should work without repeating context.

**Steps**

1. Add a `history` field to your orchestrator state: a list of prior `{question, answer}` turns.
2. Have the classification node and the SQL generation prompt receive the history so references like "their" and "that project" can be resolved.
3. Make your Lambda handler accept `history` in the request body and return the updated history in the response. Lambda keeps no memory between invocations, so the caller carries the conversation.
4. Cap how much history you replay, because every replayed turn adds input tokens to every later call. Record your cap and why you chose it.

| Requirement | Evidence | Passes when |
|---|---|---|
| Follow-ups resolve correctly | A two-turn exchange, e.g., "How many active projects does Acme Corp have?" then "What about their total contract value?" | The second query is filtered to Acme Corp, rather than returning a total across all clients |
| Works deployed | The same two-turn exchange through `aws lambda invoke`, passing history from the first response into the second request | Same result as above |
| Cost impact measured | Token usage for turn 1 vs. turn 2 | You can state how much memory added to input tokens |

### Stretch Goal B: Human-in-the-Loop Confirmation

A query can pass validation and still be one you'd want a person to look at before it runs, such as a `SELECT *` with no `WHERE` clause on a large table.

**Steps**

1. Define what counts as "unusual" in a function (for example: no `WHERE` clause, no `LIMIT`, or a join across more than two tables). Document your criteria.
2. Add a review step between SQL generation and execution. Unusual queries that pass validation do not execute. The system returns the generated SQL and the reason it was flagged, with `"needs_confirmation": true`.
3. Accept a follow-up request that confirms the exact flagged query. Only then does it execute, still through the validator.
4. Make sure a confirmation can't be used to run a *different* query than the one that was flagged.

| Requirement | Evidence | Passes when |
|---|---|---|
| Unusual queries pause for confirmation | A question that produces a flagged query | Response contains the SQL, the reason, and `needs_confirmation: true`; nothing executed |
| Confirmation executes the flagged query only | The confirming request, and an attempt to confirm with altered SQL | The original query runs; the altered one is rejected |
| Normal queries are unaffected | A routine question | Runs without a confirmation step |
| Validation still applies | A confirmed query that would fail validation | Still blocked |

**Silver is complete when Bronze plus one stretch goal pass every requirement.**

Complete Bronze, Stretch Goal A, **and** Stretch Goal B, then confirm they work together:
